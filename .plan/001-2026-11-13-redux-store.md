# 001 — Classic Redux store for the shared storefront state (revision 2)

Status: active
Owner: Idan
Last updated: 2026-11-13

Revision 2 applies the owner's review: only cart, wishlist and availability go to Redux; the checkout form and `menuOpen` stay React state; no `checkout` or `ui` domain; branch from the approved P4 commit; dependency compatibility verified; `REFACTOR_PLAN.md` and `TARGET_ARCHITECTURE.md` updated before implementation (they now describe phase P4R).

## Goal
Replace the single React Context (`StoreContext`, composed in `App.js` from `useCart`, `useWishlist`, `useAvailability`, `useCheckoutForm` and `menuOpen`) with a classic Redux store for the state that is truly shared storefront data: the cart, the wishlist and the product availability. Classic Redux only: `redux`, `react-redux`, `redux-thunk`; plain action objects, separate actions and reducer files, `combineReducers`, selectors, two thunks. No Redux Toolkit, no `createSlice`, no TypeScript. User-visible behavior, HTTP calls, services, utilities, error messages and `localStorage` persistence stay exactly as they are, known bugs included.

## Scope
In scope: the storefront cart (items and delivery method), the wishlist ids, and `unavailableIds`; removing `StoreContext`/`useStore` at the end.

Out of scope, with the reason:
- Admin hooks (`useAdmin*`, `useStatsBaseline`) and the admin session in `AdminRoute`: own lifetime, one consumer tree, already behind `adminService` (decision of the owner).
- Checkout form fields and the submit logic: stay React state in the existing `useCheckoutForm` hook (see "Checkout form: why it stays local").
- `menuOpen`: becomes `useState` in `StoreLayout`, passed to `Navbar` as props.
- The second wishlist persistence path (`utils/wishlistUtils.js`, used by the drawer and the product page) and its extra `category` field: preserved, backlog item.
- Known bugs (BF-01 variant gap in the cart, BF-07 orders list, the unguarded `localStorage.setItem` for the cart): unchanged.
- Server, database, CSS, deployment.

### Checkout form: why it stays local (and where it moves)
`CartModal` is mounted only while the URL is `/cart` or `/checkout` (`StoreLayout`: `(onCart || onCheckout) && <CartModal …/>`), and `closeCart` navigates away, which unmounts it. Today the fields live in `App`, so they survive closing and reopening the drawer. Making them state inside `CartModal` would lose them: a visible behavior change. The nearest component that stays mounted across all storefront routes and above the modal is `StoreLayout`. So `useCheckoutForm` is called in `StoreLayout` and its result is passed to `CartModal` as a prop (three children use it). No global state is needed for this.

Difference to record: the fields no longer survive a visit to `/admin` and back. There is no in-app link from the storefront to `/admin` (checked: only `<Navigate>` in `App.js`), and typing the URL reloads the page, which already resets them today.

`useCheckoutForm` keeps its return shape and its async submit (`createOrder`, 201 / 409 / failures). Its input changes from a `cartState` argument to reading the cart through selectors and dispatching two plain actions (`cartCleared`, `cartRepriced`).

## State shape (exact)
```js
{
  cart: {
    items: [              // same objects as today's cart array, same order
      // { id, name, price, quantity?, selectedColor?, selectedSize?, selectedVariant?, …product fields }
    ],
    deliveryMethod: null, // null | 'pickup' | 'delivery'   (not persisted, as today)
  },
  wishlist: {
    ids: [],              // number[]  (full records stay in localStorage, as today)
  },
  availability: {
    unavailableIds: [],   // number[], sorted ascending (a Set is not serializable)
  },
}
```
Preloaded state at store creation, with the exact try/catch of today: `cart.items` = `JSON.parse(localStorage['tamburia-cart']) || []` (any error → `[]`); `wishlist.ids` = ids of `JSON.parse(localStorage['tamburia-wishlist'])` (any error → `[]`); everything else initial.

Derived, never stored (selectors): `cartCount`, `subtotal`, `deliveryFee`, `total`, `unavailableIdSet`.

### Actions, reducers, selectors
| File | Action type (constant) | Creator | Effect in the reducer | Replaces |
|---|---|---|---|---|
| `cart/cartActions.js` | `CART_ITEM_ADDED` | `addItem(product, quantity = 1)` | merge by id + color + size, else append (body copied from `addToCart`) | `addToCart` |
| | `CART_BUNDLE_ADDED` | `addBundle(items)` | merge by id only, new lines get `selectedColor: null` (copied from `addBundleToCart`, BF-01 intact) | `addBundleToCart` |
| | `CART_ITEM_REMOVED` | `removeItem(index)` | filter by index | `removeFromCart` |
| | `CART_QUANTITY_CHANGED` | `changeQuantity(index, delta)` | `quantity \|\| 1` + delta, removes at ≤ 0 | `updateQuantity` |
| | `CART_CLEARED` | `clearCart()` | `items: []`, `deliveryMethod: null` | `setCart([])` + `setDeliveryMethod(null)` (empty-cart button and order success: always paired today) |
| | `CART_REPRICED` | `repriceCart(prices)` | match by id and `selectedVariant` (copied from `applyPrices`) | 409 handling |
| | `DELIVERY_METHOD_SET` | `setDeliveryMethod(method)` | `deliveryMethod` | `setDeliveryMethod` |
| `wishlist/wishlistActions.js` | `WISHLIST_IDS_SET` | `setWishlistIds(ids)` | `ids` | `setWishlistIds` |
| | (thunk) | `toggleWishlist(product)` | same read-modify-write on `localStorage` (stored object `{ id, name, price, image_url, in_stock }`), dispatches `setWishlistIds`; blocked or invalid storage is swallowed | `toggleCardWishlist` |
| `availability/availabilityActions.js` | `AVAILABILITY_LOADED` | `availabilityLoaded(ids)` | `unavailableIds` (sorted array) | `setUnavailableIds` |
| | `AVAILABILITY_CLEARED` | `availabilityCleared()` | `[]` (same reference if already empty) | the empty-key branch |
| | (thunk) | `checkAvailability(key)` | empty key → clear, no request; otherwise `getProducts({ ids: key, signal })`, ids missing from the answer are unavailable; failure leaves the state; returns an abort function used as the effect cleanup | `useAvailability` effect |

Selectors: `cart/cartSelectors.js` — `selectCartItems`, `selectDeliveryMethod`, `selectCartCount`, `selectSubtotal`, `selectDeliveryFee`, `selectTotal` (use `sumPrices`, `lineTotal` from `utils/pricing.js` and `DELIVERY_FEE` from `utils/delivery.js`, so the agorot arithmetic is unchanged). `wishlist/wishlistSelectors.js` — `selectWishlistIds`. `availability/availabilitySelectors.js` — `selectUnavailableIds`, `selectUnavailableIdSet` (memoized by array identity so consumers get a stable `Set`), `selectAvailabilityKey` (the deduped, sorted, 100-capped id string from `useAvailability`).

Action types live in the actions file (constants exported next to the creators): no separate `actionTypes` files. Reducers are pure and return the same state reference when nothing changes.

12 files plus their tests. Test files sit next to their file as `<name>.test.js` (naming rule). Redux terms (store, action, reducer, selector, thunk) are added to `.doc/glossary.md` before first use. `context/` is deleted at the end.

## How components read and dispatch
- Reading: `useSelector(selectCartCount)`, one narrow selector per value. Never `useSelector((s) => s)`.
- Writing: `const dispatch = useDispatch(); dispatch(addItem(product, qty))`.
- `Provider` is rendered inside `App.js` (`App` becomes `<Provider store={store}><AppRoutes/></Provider>`), so `index.js` and `App.test.js` do not change. A store module is a singleton for the app; tests build stores from a given state through `createStore`.
- Availability is kept in sync by one small hook used in `AppRoutes`: `useEffect(() => dispatch(checkAvailability(key)), [key])` with `key = useSelector(selectAvailabilityKey)` (the thunk returns the abort function, which is the cleanup). It runs whether or not the cart drawer is open, exactly as `useAvailability` does today, so the "unavailable" marks are ready when the drawer opens.
- Temporary facade: `useStore()` stays during the migration, returning the old key set from Redux selectors plus the not-yet-migrated parts of the old context. Deleted in the last step.
- Services (`productService`, `orderService`, `pigmentService`, `authService`, `adminService`), `http.js`, `utils/*`, messages: called unchanged.

## Assumptions
- `useStore()` is read by `Navbar`, `CartModal`, `CartStepView`, `CheckoutFormView`, `DeliveryOptions`, `OrderSuccessView`, `RelatedProducts`, `CategoryPage`, `HomePage`, `ProductPage` and `StoreLayout`; `menuOpen` is read only by `Navbar` and `StoreLayout`; `setCart`/`setDeliveryMethod` outside `useCart` and `useCheckoutForm` are used only by the empty-cart button in `CartStepView`.

### Deviations found during execution
1. **`useAvailability` stays.** `RelatedProducts` also calls it, for the recently viewed list (local, one consumer, not shared state). The store covers the cart's availability only; the hook is untouched and keeps its own tests. The key and request logic is therefore written twice (hook and thunk); a shared helper is a follow-up, not done here.
2. **No temporary `useStore()` facade.** The consumers are few and small, so each was moved to selectors and `dispatch` directly, domain by domain, with the UI-level pin tests (`App.cart.test.js`) unchanged and green throughout. The key-set pin was therefore dropped with the facade it guarded.
3. **`setCart` no longer exists.** Its only callers were the empty-cart button and the checkout (clear after success, re-price after a 409), now `clearCart` and `repriceCart`.
4. **One expected value changed in `useCheckoutForm.test.js`:** the old fixture handed the hook arbitrary totals (fee 40, total 570); the hook now reads the cart, so the request carries the derived fee 20 and total 550. Every other assertion is unchanged.
5. **`createAppStore()` is a factory called once per `App` mount** (`useState` initializer) instead of a module singleton, so each mount reads `localStorage` once, like the hooks did, and tests can build stores from a given state.
6. **A cart line without a price gives `NaN` sums** in the selectors, as it did in the hook (the screens block such a cart with `itemPriced`); not changed.

## Risks
- **Cart persistence:** today a `useEffect` writes the cart on mount and on every change; a subscriber that writes only on change would skip the first write, so an invalid stored value would not be overwritten with `[]`. Mitigation: write once at store creation; pinned in step 3(b). The cart write is not wrapped in `try/catch` today and stays so (known behavior).
- **Cart merge semantics:** `addItem` matches id, color, size (not variant), `addBundle` matches id only. Mitigation: reducer bodies copied unchanged; BF-01 stays a "current behavior" test.
- **409 re-pricing:** `setCart((prev) => applyPrices(prev, prices))` becomes the `CART_REPRICED` action; matching by id and variant is copied from `applyPrices`.
- **Order success:** `setCart([])` and `setDeliveryMethod(null)` become one `CART_CLEARED`; verified they are always paired (empty-cart button, order success).
- **Unnecessary re-renders:** the Context re-renders every consumer on any change; Redux re-renders only subscribers whose selected value changed. A selector that returns a new array or object each time re-renders always. Mitigation: narrow selectors; reducers return the same reference when nothing changes; `selectUnavailableIdSet` memoized; the facade (the only broad reader) is temporary. The checkout hook moving into `StoreLayout` re-renders the layout on each keystroke, like `App` does today (no worse).
- **Authentication:** unchanged and outside Redux. The `createAdminApi(onUnauthorized)` wiring in `Admin.js` is not touched.
- **Two wishlist paths:** the drawer and product page read `localStorage` directly while the cards read store ids; they can disagree until the drawer re-reads on open (and the stored objects differ by a `category` field). Preserved on purpose; backlog item.
- **Availability race:** the request is keyed by the id list and aborted on change; the thunk keeps the abort and ignores a late answer after abort.
- **Jest 27 and the packages' module formats** (see Verified facts). Mitigation: the step-2 gate and the `moduleNameMapper` fallback.
- **Stacked pull requests:** this branch builds on unmerged P1–P4. Mitigation: retarget to `main` after the P1–P4 pull request merges; the owner decides the merge order.
- **Test coupling:** `CategoryPage.test.js`, `ProductDetails.test.js`, `useCart*.test.js`, `useCheckoutForm.test.js` use the hooks or `StoreContext`. Mitigation: the facade keeps them valid; each is adapted only in its setup, never in its assertions (the P2 rule).
- **Bundle size:** the three packages are added to the main bundle (the storefront needs them); the size is measured, not assumed.

## Rollback
Each step is its own commit and is reverted alone with `git revert`. Steps 5 to 7 keep the facade, so reverting one domain leaves the others working. Until the last part of step 9 nothing is deleted, so the whole phase can be dropped by deleting `store/` and the `Provider` in `App.js`. The dependency commit (step 2) reverts independently. After step 9, rollback is a revert of the removal commits, which restores the Context, the facade and the three hooks. The branch can be abandoned without touching the P1–P4 branch.
