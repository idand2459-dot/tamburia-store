# 006 — p10 portfolio demo deployment

Status: draft
Owner: Idan
Last updated: 2026-11-16

## Goal
Put Technic Tambur online as a public **portfolio demonstration** for junior Full Stack interviews: one Node.js web service (Express API and the React build, one origin) on Render, a Neon PostgreSQL database that holds only demo data, no real orders, payments, customer notifications or emails, and a visitor who always knows it is a demo. Two admin experiences: a public **read-only viewer** and a private **owner** with full editing, both enforced on the server. This is not a commercial launch; the commercial checkout is not assumed safe to expose, so demo mode is enforced by the server and the database, not by hiding buttons.

## Scope
In scope: `DEMO_MODE` and PostgreSQL TLS configuration; a database identity marker and an explicit first-time bootstrap; a deterministic, guarded seed; two admin roles (`owner`, `viewer`) in the existing signed token with default-deny authorization; demo-only checkout with three fixed fictional identities; reliable bounded cleanup and abuse limits; a curated catalogue, reviewed pigment formulas and a static image set taken from the existing project; build and environment settings; tests; documentation and an interview explanation.
Out of scope, deliberately: a custom domain, real payments or email, an email outbox, Cloudinary or Cloudflare R2 (only if static packaging proves unsuitable), Docker, Redis, a CDN, a general RBAC framework (two roles only), keep-alive pings, paid hosting, CSP hardening, privacy and terms pages (a commercial launch needs them; they stay in the backlog), merging the old `feat/cloud-deploy` branch, and any change to the cart, pricing, availability or order-idempotency logic. Image uploads keep working outside demo mode. Redux stays classic, PostgreSQL stays without an ORM, availability stays the boolean `in_stock`, categories stay in `client/src/js/features/catalog/categories.json`.

## Decisions already made by the owner
1. One Node.js service serves the API and the React build; one origin, relative `/api` requests, the existing cookie architecture.
2. Render for the application, Neon for PostgreSQL; their current terms are re-verified before any account is created.
3. Isolated demo database; free-tier cold starts accepted; no keep-alive requests and no paid hosting.
4. The public demo admin is read-only and the private owner admin keeps full editing, both on the deployed site, with server-enforced role separation.
5. **Image uploads are disabled in the deployed demo for everyone, the owner included.** Upload keeps working unchanged outside demo mode.
6. **Public review submission is disabled in demo mode**; curated demo reviews stay.
7. **Three predefined fictional customer identities.**
8. **Visitor demo orders are kept 72 hours, at most 100 active at a time.**
9. **Pigment formulas are reviewed by the owner before they are published in the demo.** That the migration is already in the public Git history is not permission to publish them in the demo.
10. **About 36 curated existing products** with adjusted demonstration prices and owner-approved images; the whole of `uploads/`, `uploads-originals/`, `photos/` and `design-assets/` is never deployed.

## Assumptions
**Verified in the repository (2026-11-16):**
- One process serves `/api`, `/uploads` and the React build (`server/app.js`); the client calls relative `/api/...` paths.
- The admin token is `base64url(payload).base64url(HMAC-SHA256)` with `sub: 'admin'`, `iat`, `exp` and no role; the cookie `tamburia_admin` is `httpOnly`, `sameSite: 'strict'`, `secure` in production (`server/api/auth/auth.service.js`). `requireAdmin` verifies the token; `markAdmin` only reveals hidden products.
- Routes behind `requireAdmin` today: orders (list, stats, one, update, delete, status, picked), products (create, update, delete), pigment formulas (create, update, delete), reviews (all, one, update, delete, approve), settings (get, update), `POST /api/upload-multiple`, `GET /api/auth/me`. `POST /api/orders` and `POST /api/reviews` are public and rate limited.
- `server/server.js` runs `assertConnection` and then `runMigrations` at every start; each migration runs in its own transaction with no lock. A fresh empty database is supported (`000_products_base.sql`, covered by `test/smoke-fresh-db.js`). `settings` is created by migration 007, so **it does not exist on a fresh database**.
- `server/config/db.js` has no `ssl` option; `MAIL_ENABLED` defaults to **enabled** when unset (`process.env.MAIL_ENABLED !== 'false'`).
- **Order responses never carry `request_id` or `request_hash`:** the order repository selects an explicit column list (`id, customer_name, customer_phone, customer_email, delivery_method, delivery_address, notes, items, subtotal, delivery_fee, total, status, created_at, picked_items`), and `request_hash` is read only by the replay lookup. `request_id` must be a version-4 UUID when it comes through the API (`asRequestId` in `order.validator.js`), the owner's order edit is limited to seven customer and status fields (`EDITABLE`), and the unique index `orders_request_id_key` is partial on `request_id IS NOT NULL`.
- **Read paths audited (GET and HEAD, admin or `markAdmin`):** `GET /api/orders`, `/api/orders/stats`, `/api/orders/:id`, `GET /api/reviews/all`, `/api/reviews/:id`, `GET /api/settings/:key`, `GET /api/auth/me`, and the public product and pigment GETs. Each goes controller → service → repository `SELECT` with an explicit column list; none writes. `GET /api/products` with `markAdmin` additionally returns hidden products (`active = false`). In a real database these responses hold customer names, phones, emails, addresses and review text, so a viewer role is safe **only** because a demo database never contains real values (Phase 4).
- `pigment_formulas` holds 20 rows seeded by migration `005_pigment_formulas_seed.sql` (a Hebrew colour name, a hex value and three millilitres-per-litre dosages), which says it does not overwrite manual changes; the real database may therefore differ from the migration. The formulas are public through `GET /api/pigment-formulas` and the paint calculator uses them.
- The catalogue has 408 products in 11 categories (`design-assets/product-list.csv`, generated earlier: tools 142, painting 44, electrical 39, locks 39, plumbing 38, bathroom 33, home 24, cleaning 22, adhesives 20, garden 5, faucets 2; 124 rows with price 0 and 108 without SKU). Its `has_real_image` column is stale (1 of 408) while `uploads/` holds 219 files, so the product-to-image link must be recomputed from the database at selection time. The database itself was not read (its credentials are in an env file the agent may not read).
- Uploaded images are content-named WebP, square 1200 px, metadata stripped (`server/services/image.service.js`); product photographs are taken in the shop by the owner (`docs/product-photos.md`).
- The calculators choose products by `category` and `subcategory`, not by SKU, so SKUs can be replaced; a curated catalogue must cover the pairs they ask for.
- The GitHub repository is **public** (`gh repo view`, read-only): anything committed for the demo is world-readable and stays in history.
- Reused guardrails: `docs/security.md` deployment checklist, `unit-config`, `unit-repo-hygiene`, `unit-no-private-phone`, the test-database guard (`test/lib/testDatabase.js`), and `PROJECT_DENY_PATTERNS` in `.claude/hooks/block-destructive-bash.mjs`.

**Provider facts found by a web search on 2026-11-16 (re-verify on the official pages before creating an account):**
- Render: a free web service spins down after 15 minutes without inbound traffic and takes about a minute to wake; its filesystem is ephemeral; 750 free instance hours per workspace per month; 512 MB RAM and 0.1 CPU; pre-deploy commands are paid-only; deploys are zero-downtime (the new instance starts beside the old one); free Render Postgres expires after 30 days (not used).
- Render's proxy appends to `X-Forwarded-For` and does not filter a client-supplied value; community answers say services sit behind Cloudflare. The number of proxies is **not** officially documented, so `TRUST_PROXY_HOPS` is decided by the live test, not by assumption.

## Steps
The branch `feat/p10-portfolio-demo` already exists (one workstream, one branch). Execution starts only after the owner approves this plan and sets its Status to `active`. Each phase is one reviewable change set; the owner stages and commits.

### Phase 1 — Demo configuration and PostgreSQL TLS
- **Files:** `server/config/env.js`, `server/config/db.js`, `.env.example`, `test/unit-config.js`, `test/unit-repo-hygiene.js`.
- **Changes:**
  - New variables: `DB_SSL` (boolean, default false), `DEMO_MODE` (boolean, default false), `DEMO_DATABASE_ID` (a UUID), `DEMO_MAX_VISITOR_ORDERS` (default 100), `DEMO_ORDER_TTL_HOURS` (default 72).
  - `DB_SSL=true` passes `ssl: { rejectUnauthorized: true }` to the `pg` Pool, so the certificate chain and host name are verified against Node's trusted authorities. Nothing in the code may set `rejectUnauthorized: false` or `NODE_TLS_REJECT_UNAUTHORIZED`. If a provider's chain fails verification, the fix is to supply its CA through a documented `DB_SSL_CA` path variable, never to disable verification.
  - With `DEMO_MODE=true` the server refuses to start unless `NODE_ENV=production`, `MAIL_ENABLED` is explicitly `false`, `DEMO_DATABASE_ID` is a UUID, `ADMIN_PASSWORD` is at least 20 characters, `SERVE_CLIENT` is true and `CORS_ORIGINS` is empty. Messages name the variable only.
  - Placeholders added to `.env.example`; no secret.
- **Tests and acceptance:** `unit-config` covers each refusal and accepted combination; `unit-repo-hygiene` fails on `rejectUnauthorized: false` and `NODE_TLS_REJECT_UNAUTHORIZED` in `server/`, `scripts/` and `test/`; `npm test` stays green with `DEMO_MODE` unset.
- **Dependencies:** none. **Risks:** a refusal message that prints a value (naming-only convention plus a test). **Rollback:** revert the commit; no data is touched.

### Phase 2 — Database isolation, first-time bootstrap and normal startup
This phase separates two things that must never be mixed: the **first-time bootstrap** of a fresh database (an owner-run script) and **normal startup** (the server). Only the bootstrap can create the marker. The server never does.

- **Files:** `server/api/demo/demo.repository.js`, `demo.service.js`, `demo.routes.js`, `demo.controller.js` (new; Controller → Service → Repository), `server/server.js`, `server/api/index.js`, `server/db/migrate.js`, `scripts/demo-bootstrap.js`, `scripts/demo-seed.js`, `scripts/lib/demoTarget.js`, `scripts/demo-data/` (data, filled in Phases 4 and 5), `package.json` (`demo:bootstrap`, `demo:seed`), `.claude/hooks/block-destructive-bash.mjs` (deny patterns, same commit), `test/unit-demo-target.js`, `test/smoke-demo-bootstrap.js`, `test/smoke-demo-database.js`, `test/run-all.js`.
- **The marker:** a demo-only table `demo_database_marker` (one row, enforced by a primary key on a constant): `id` (UUID), `state` (`bootstrapping` or `ready`), `created_at`. It is **not** in a migration, so a real database can never contain it, and it must exist before any migration, which is why it cannot live in `settings` (a fresh database has no `settings`). A PostgreSQL database comment was considered and rejected: it needs database ownership (unverified on a managed host) and is invisible to ordinary SQL tooling.
- **First-time setup sequence (owner-run, once, `npm run demo:bootstrap`):**
  0. Preconditions: the owner creates a **new, empty** Neon project in the dashboard for this purpose and, in the current PowerShell session only, sets `DEMO_DATABASE_URL` (the direct host). It is never written to a file, a command line argument, a chat or a log.
  1. *Read-only identity phase — no write and no DDL.* The script parses the URL and refuses if it is missing, malformed, carries query parameters, points at the development database (same host, port and name as `DB_*`) or the test database, or at a local host without `--allow-local`. It requires `--confirm-host <host>` and `--confirm-database <name>`, each typed by the owner and equal to the URL's. It connects with TLS verification, prints the host, database and role (never the password), checks that `current_database()` equals the confirmed name, and checks that the database is **pristine**: no table, view, sequence or function outside the system schemas. A database that already has anything in it is refused here, which is exactly what protects a real or development database. There is no flag that skips this check.
  2. *Claim.* One transaction creates `demo_database_marker` and inserts a new random `id` with `state = 'bootstrapping'`. From now on the database is no longer pristine and belongs to the demo. The script prints the `id` once; the owner stores it as `DEMO_DATABASE_ID` in Render.
  3. *Schema.* `runMigrations()` runs under an advisory lock.
  4. *Seed*, in one transaction: reviewed pigment formulas (upserted over the migration's values by `color_code`), curated products, curated reviews, tagged demo orders; then `state` is set to `ready` as the last statement.
  - *Failure and resume:* a crash after step 2 leaves `state = 'bootstrapping'`. The server refuses to serve such a database. `npm run demo:bootstrap -- --resume --database-id <id>` (with the same typed confirmations) repeats steps 3 and 4, which are idempotent, and only if a marker with that id and `bootstrapping` exists.
  - *Later runs:* `npm run demo:seed` (refresh the curated rows) and `npm run demo:seed -- --reset` (also delete every visitor order and re-anchor seeded dates) require a `ready` marker, the matching `--database-id`, and the same typed confirmations. Neither can claim an unmarked database.
  - Deterministic and idempotent: fixed order, fixed values, upserts by natural keys (products by explicit demo id, reviews by explicit id, pigment formulas by `color_code`, demo orders by their `request_id` tag, Phase 6). Only seeded `created_at` values move, because they are anchored to the run time.
  - `PROJECT_DENY_PATTERNS` gets patterns for both npm scripts and both files in the same commit (AGENTS.md rule for scripts that write to a remote database). The agent never runs them.
- **Normal startup (`server/server.js`), by contrast, only verifies and never claims:** connect, then `SELECT to_regclass('public.demo_database_marker')` (null, not an error, when absent), then decide **before any write**:
  - `DEMO_MODE=true`: the table must exist, hold one row whose `id` equals `DEMO_DATABASE_ID`, with `state = 'ready'`; otherwise exit.
  - `DEMO_MODE` off: if the table exists, exit ("this database belongs to a demo").
  - Only then `runMigrations()` (new migrations after a deploy; the marker table is never touched).
  So a demo server pointed at the real database changes nothing there, a normal server pointed at the demo database cannot start, and nothing at startup can mark an arbitrary database.
- **Migrations at startup, reviewed:** idempotent (`IF NOT EXISTS`), each in its own transaction, recorded in `schema_migrations`. Render's zero-downtime deploy starts a new instance beside the old one, so two processes can migrate together. Mitigation: `runMigrations` takes a `pg_advisory_lock` on one dedicated connection and releases it in `finally`; this needs Neon's **direct** host (a pooled host would not keep a session lock), documented in the environment list. Pre-deploy commands are paid-only, so migrations stay in the start path.
- **Tests and acceptance:**
  - `unit-demo-target`: URL translation and every refusal, with fake URLs only.
  - `smoke-demo-bootstrap`, on a scratch database that the suite creates and drops on the local server (it needs the `CREATEDB` privilege; without it the suite prints an explicit "not run" and the run is reported as incomplete, never as passed): refuses a database containing any table; refuses without matching typed host and name; refuses the development and test database names; refuses a local host without `--allow-local`; succeeds on a pristine database and ends with `ready`; a forced failure in the seed leaves `bootstrapping`; the server refuses `bootstrapping`; resume works only with the right id; a second bootstrap on a claimed database is refused; `demo:seed` refuses an unmarked database, a wrong id, and a database with products and no marker.
  - `smoke-demo-database` on the guarded test database: demo server refuses without the table, with a wrong id, and with `bootstrapping`; a normal server refuses with the table; a refusal changes no table; two concurrent `runMigrations` calls both succeed. Suites remove the marker in `finally`, and a leftover marker gives a clear message.
- **Dependencies:** Phase 1. **Risks:** the owner mistypes the target (typed host and name, pristine rule); a half-finished bootstrap (state flag and resume); a leftover marker in the test database (cleanup, message). **Rollback:** revert the commits; delete the Neon project; nothing local is affected.

### Phase 3 — Public read-only demo admin and private owner admin (default-deny)
- **Evaluation of the existing authentication:** the stateless HMAC token can carry two roles safely with a small change: a signed `role` claim (`owner` or `viewer`). A client cannot change it without `SESSION_SECRET`, because the signature covers the payload, and the `httpOnly` `SameSite=Strict` cookie cannot be set by page scripts. The known weakness stays and is documented: no server-side revocation (backlog S-09); the answers are a 4-hour viewer lifetime (a code constant) and rotating `SESSION_SECRET`.
- **Files:** `server/api/auth/auth.service.js`, `auth.controller.js`, `auth.routes.js`, `auth.validator.js`, `server/middleware/requireAdmin.js`, the route files of orders, reviews and settings (the viewer-readable GET lines only), `server/api/index.js`; client: `services/authService.js`, `pages/AdminLogin.js`, `routes/AdminRoute.js`, `pages/admin/Admin.js`, `AdminTabs.js`, `adminConstants.js`, `OrdersTab.js`, `OrderCard.js`, `ReviewsTab.js`, `ProductsTab.js`, `AdminProductCard.js`, `StatsTab.js`, a small `pages/admin/adminAccess.js` context carrying the role, the admin CSS partial for the read-only note.
- **Server design — the method alone is not trusted; viewer access is an explicit allowlist:**
  - `createToken(role)` and `verifyToken` require `role` to be `owner` or `viewer`; a token without a role (issued before this change) is invalid, so the owner logs in again once.
  - `POST /api/auth/login` issues `owner` and is otherwise unchanged. `POST /api/auth/demo-login` issues `viewer` with no password, uses the same login limiter, and is mounted **only when `DEMO_MODE=true`** (404 otherwise), so a viewer token cannot be obtained on a normal server.
  - **`requireAdmin` becomes owner-only.** Every existing write route already uses it and needs no edit, so every write is default-deny for the viewer, and so is every future route, whatever its method (a new GET with `requireAdmin` is invisible to the viewer until someone deliberately changes it).
  - A new **`requireAdminRead`** accepts owner and viewer, and **only for GET and HEAD** (any other method gets 403 whatever the role, a second line of defence). It is applied to exactly these routes: `GET /api/orders`, `/api/orders/stats`, `/api/orders/:id`, `GET /api/reviews/all`, `/api/reviews/:id`, `GET /api/settings/:key`, `GET /api/auth/me`. `markAdmin` is unchanged and accepts both roles (the viewer sees hidden products, which are demo products).
  - A viewer who reaches an owner-only route gets 403 with a Hebrew message and a stable reason (`demo_read_only`, in `details`, in the error-handling skill's shape). `GET /api/auth/me` returns `{ authenticated, role, expiresAt }`; the client uses it only to choose what to render.
  - `ADMIN_PASSWORD` in the demo environment is the private owner password (at least 20 characters, enforced in Phase 1); the real shop's password is never used there.
- **What a viewer can read, and why it is safe:** the audit above shows every viewer-readable endpoint is a plain `SELECT` with an explicit column list. The viewer sees orders (customer fields, items, totals, status), reviews (reviewer name, text, rating), products including hidden ones, aggregate statistics and one timestamp setting. In the demo database every customer and reviewer value belongs to a fixed fictional set (Phase 4), so there is nothing private to protect or to sanitize on the way out. `request_id` and `request_hash` are never in a response. A test proves the claim from the data, not from a promise: after every suite run, the invariant check reads every order and review row and fails if any customer field is outside the allowed fictional set.
- **Client:** the login screen shows "כניסה כצופה (הדגמה)" in demo mode; controls that write (status change, picked toggles, order edit and delete, product add, edit, hide and delete, review approve and delete, the statistics reset, the import and product-form tabs) are hidden or disabled for `viewer` with a short read-only note. This is presentation only; each action also fails on the server if forced.
- **Authorization tests (focused, table-driven):** `test/smoke-admin-roles.js`, one row per protected endpoint with a sample body, checked with no cookie (401), a viewer cookie (the seven allowlisted reads 200; **every other row 403 and no row changed**, counted before and after), and an owner cookie (not 401 or 403). Read-only proof: after calling every viewer-readable endpoint (GET and HEAD), the contents of every table are identical to before. Exposure proof: viewer responses contain no `request_id`, `request_hash`, password or secret key, and every customer value is in the fictional set. Escalation attempts: a payload with the role changed but the old signature; a token signed with another secret; a legacy token without a role; a `role` in the body, query or headers; `X-HTTP-Method-Override` and `_method`; a viewer posting to `/api/auth/login` with a guessed password (rate limited); `demo-login` returning 404 when `DEMO_MODE` is off. `test/unit-admin-routes-covered.js` reads the `*.routes.js` files (a source scan in the style of `unit-repo-hygiene`, not a router inspection) and fails if a route uses `requireAdmin` or `requireAdminRead` without a row in the table, or if `requireAdminRead` appears on anything other than `router.get`. `unit-auth-cookie` is updated for the role. Client tests: the viewer button appears only in demo mode, write controls are absent for a viewer, a 403 shows the read-only message.
- **Acceptance:** every admin write and every non-allowlisted read is 403 for the viewer and works for the owner; existing admin tests pass with an owner login. **Dependencies:** Phase 1; Phase 4 for the data guarantee. **Risks:** a forgotten client control is harmless (the server refuses); a future GET attached to `requireAdminRead` by mistake is caught by the table and the source scan. **Rollback:** revert; existing sessions become owner sessions after re-login.

### Phase 4 — Demo-only checkout, no uploads, no public reviews
- **Principle:** protect by what can be **stored**, not by what is displayed. In demo mode the server accepts an order only if its customer fields exactly match one of three fixed fictional identities, so the database never holds a visitor's real data.
- **Files:** `server/api/demo/demo.rules.js` (the identities, the allowed notes and the order-tag prefix; one source for server, seed and tests), `server/api/order/order.service.js` (one call at the start of create, and one on update for the merged state), `server/api/review/review.service.js`, `server/api/upload/upload.routes.js` (a demo-disabled guard before `multer`), `server/api/demo/demo.service.js`; client: a `DemoBanner` component in `client/src/js/components/`, a `useDemoMode` hook (reads `GET /api/demo` once; no Redux slice is added), `features/cart/CheckoutFormView.js` and `hooks/useCheckoutForm.js`, the reviews form, the admin product form (upload control), `StoreLayout.js` and `pages/admin/Admin.js` (banner), CSS partials `client/src/css/components/_demo-banner.css` and, if needed, one under `client/src/css/features/cart/`, imported in `app.css` without reordering.
- **Server rules:**
  - Three identities, each a fictional name (at most 30 characters, the existing limit), a phone in the unassigned `050-00000xx` block the existing demo seed uses, an email on the reserved `example.invalid` domain, and an address on a fictional street in an allowed delivery city. `notes` must be empty or the fixed text; a pickup order carries no address. Anything else is a 400 with a Hebrew message. The same rule applies to the owner's order edit (merged state).
  - `POST /api/reviews` returns 403 (reason `demo_disabled`) in demo mode; `GET /api/reviews` and `/stats` work, and seeded reviews, approved and pending, let the owner demonstrate moderation.
  - `POST /api/upload-multiple` returns 403 (`demo_disabled`) in demo mode **for every role, the owner included**, before `multer` reads any file; outside demo mode it is unchanged. The admin product form hides the upload control in demo mode; products keep the bundled images, and a product created in the demo has none and shows the category icon fallback. No image is ever written to the host's ephemeral disk in demo mode.
  - Mail: `MAIL_ENABLED=false` is mandatory (Phase 1) and the transporter then only logs a label. No payment code exists.
  - Unchanged and covered by existing suites: idempotency by `request_id` with the payload hash, availability and `option_unavailable` 409, repricing 409, order limits, per-address rate limits (set lower in the demo environment, for example 5 per 15 minutes), the transaction with its `FOR SHARE` lock on ordered products, and no public order lookup (`GET /api/orders/by-phone` stays a 404; the order GETs stay admin-only).
- **Client behavior:** a persistent Hebrew banner in the store and the admin, for example: "אתר הדגמה לפרויקט תיק עבודות — כל הנתונים פיקטיביים. הזמנות אינן מטופלות, לא נשלחים מוצרים, לא נגבה תשלום ולא יישלח מייל." The checkout has a "מילוי פרטי הדגמה" button that fills the three read-only fields from one of the identities, and a notice under the submit button. Cart, drawer, delivery choice, price checks and the thank-you screen are unchanged.
- **Tests and acceptance:** `test/smoke-demo-checkout.js`: a demo-identity order is created (201) and appears in the admin; a real-looking name, phone, email, address or notes is refused (400) and nothing is stored; the same `request_id` replays with 200 and `Idempotent-Replayed`; an unavailable product still returns 409; the rate limit still returns 429; no mail send is attempted; `GET /api/orders/:id`, `/api/orders` and `/stats` without a cookie are 401; review creation and `POST /api/upload-multiple` are 403 for visitor, viewer and owner in demo mode and work as before outside it; the data-invariant check passes. Client tests: banner, fill button, read-only fields, hidden upload control, unchanged non-demo checkout. `npm run test:e2e` still passes outside demo mode.
- **Dependencies:** Phases 1 and 2. **Risks:** a code path that writes orders without the service (none exists; the invariant check would catch one). **Rollback:** revert; demo mode off restores the commercial behavior.

### Phase 5 — Curated existing products, reviewed pigment formulas and static images
- **Sources inspected:** the products table (migrations 000, 001, 006, 008, 009, 010: `name`, `price` NUMERIC, `image_url`, `images` JSONB, `category`, `subcategory`, `colors` JSONB, `sizes`, `sku`, `description`, `in_stock`, `variants` JSONB, `image_illustrative`, `active`); `scripts/products_import_template.csv` and the import scripts (they carry real SKUs); `uploads/` (219 content-named WebP files); `uploads-originals/` (never shipped); `photos/`; `design-assets/` (none is shipped); `categories.json`; `pigment_formulas`.
- **Selection procedure (nothing is copied until the owner approves a list):**
  1. A new read-only script `scripts/demo-candidates.js`, owner-run against the development database, writes only ignored files `design-assets/demo-candidates.csv` and `.html` (like `products:list`). Products: active, `in_stock`, priced above zero, primary image file present in `uploads/`, with a thumbnail, category, subcategory, a suggested demonstration price, and warnings (a phone number, URL, email, WhatsApp text, a supplier or importer word, a street address). It also prints whether each (category, subcategory) pair the calculators ask for is covered. Pigment formulas: the 20 rows as they are in the development database next to the migration's defaults, so the owner sees any manual tuning.
  2. The owner marks about 36 products (fewer if fewer have a verified photo): at least two per category where photographs exist; the calculator pairs covered; three products with colors, sizes or variants; three out of stock and two hidden (`active = false`) to show availability and admin behavior; two with `image_illustrative`; no price 0. For the formulas, per row: publish the real dosages, or replace them with demonstration dosages (the default, Open Question 3). Colour names and hex values are generic and are kept.
  3. After approval, a new owner-run `scripts/demo-catalogue-build.js` writes `scripts/demo-data/catalogue.json` and `scripts/demo-data/pigment-formulas.json` and copies only the chosen image files into a new tracked folder `demo-assets/uploads/`. The agent copies nothing before approval.
- **Field policy:**

| Field | Decision |
|---|---|
| `id` | renumbered 1..N, stable in the file (no link to production ids) |
| `name`, `category`, `subcategory`, `colors`, `sizes` | kept; name reviewed against the warning list |
| `description` | kept after review; rewritten when it names a supplier, importer, contact or address |
| `sku` | replaced by `DEMO-001`..; the real SKU (a supplier or internal code) is never published |
| `price` and variant prices | demonstration prices (rounded), checked by the product validator; variant structure unchanged |
| `in_stock`, `active`, `image_illustrative` | set deliberately, as above |
| `image_url`, `images` | only `/uploads/<name>.webp` names of bundled files |
| pigment formulas | reviewed per row as above; written by the bootstrap over the migration's values |
| customer, order, review and settings data | never copied; demo orders and reviews are written by the seed from `scripts/demo-data/` |

- **Images:** the owner confirms from the preview sheet that each image shows only the product (no person, face, vehicle, phone number, receipt, supplier catalogue page, or shop interior with names) and that the owner took it or holds the right to publish it; any doubt drops the image. Files are already content-named WebP without metadata; the whole set stays under 8 MB. Because the repository is public, curation happens **before** the commit; removing a file later does not remove history.
- **Delivery to the host:** the Render build runs a small `scripts/demo-copy-images.js` that copies `demo-assets/uploads/` into `uploads/` (git-ignored). The set is rebuilt on every deploy, so it survives restarts. **Uploads cannot persist on Render's ephemeral disk**, which is why they are disabled in demo mode (Phase 4); the bundled set is the only image source.
- **Tests and acceptance:** `test/unit-demo-catalogue.js`: every catalogue entry passes the product validator; every referenced image exists in `demo-assets/uploads/` and every file there is referenced; each file name equals its content hash; no SKU outside `DEMO-###`; no phone, URL, email or WhatsApp pattern in any text; no price 0; the size limit; pigment rows valid. The owner checks the calculators in the demo (a missing pair shows "שאל בחנות", acceptable but visible).
- **Dependencies:** Phase 2. **Risks:** an unreviewed image, description or dosage becomes public (the owner's approval gate and the scans); calculator gaps (the coverage report). **Rollback:** delete `demo-assets/` and `scripts/demo-data/`; nothing existing is moved or changed.

### Phase 6 — Reliable cleanup and abuse protection
- **Constraint:** a Render free instance sleeps, so no timer is relied on. Cleanup is **bounded work done on events that wake the process**, safe to run at any time and any number of times.
- **How a visitor order is told from a seeded one — options, from the actual schema** (`orders`: `id`, customer fields, `items`, totals, `status`, `created_at`, `picked_items`, `request_id`, `request_hash`):

| Option | Verdict |
|---|---|
| A. `seedOrderMaxId` in the marker (id boundary) | Rejected. Seeded and visitor orders share one sequence; adding seeded orders later, or a changed sequence, makes a seed upsert collide with a visitor id or cleanup cross the boundary. |
| B. `request_id IS NOT NULL` means visitor | Rejected. Implicit; the field is optional on the server, so an order without it would look seeded or unrelated. |
| C. A new column such as `orders.demo_kind` (migration 013) | Explicit and simple, but it changes the real database's schema, the column list and the model for a demo-only concept. Kept as the fallback if the owner prefers it. |
| D. A side table of seeded order ids | Demo-only DDL and a join; more moving parts than needed. |
| **E. Seeded orders carry `request_id = 'demo-seed:NN'` (recommended)** | No schema change. The seed upserts through the existing partial unique index (`ON CONFLICT (request_id) WHERE request_id IS NOT NULL`), so it needs no fixed order ids at all. The public API cannot produce the tag, because it accepts only a UUID v4 (`asRequestId`); the owner's edit cannot change `request_id` (`EDITABLE`); and `request_id` is never returned (explicit column list). Trade-off: a convention that overloads the column, enforced by tests rather than by a constraint. |

- **Cleanup design (`demo.service.js`, `demo.repository.js`):**
  - A **visitor order** is an order whose `request_id` is null or does not start with `demo-seed:`, **and** whose `customer_phone` belongs to the three allowed identities. The second condition is defence in depth: a row that is not recognisably demo data is never deleted.
  - `cleanupExpired()` runs one statement: delete up to 200 visitor orders with `created_at` older than `DEMO_ORDER_TTL_HOURS` (default 72). It never touches products, reviews, settings, pigment formulas, the marker or seeded orders. `request_id` and `request_hash` live in the same row, so idempotency data goes with the order and nothing is orphaned; a retry that arrives after the purge creates a new order, which the 72-hour window (longer than the client's 48-hour recovery) makes practically unreachable and is documented.
  - It first re-reads the marker (cached after startup, re-read before a delete) and does nothing if it is missing, differs, or is not `ready`.
  - Triggers: at startup after the identity check; at the start of demo order creation; when an admin reads the order list or statistics. The last two are throttled to one run per five minutes per process; order creation also runs it when the cap is reached. A server that was asleep cleans up when it wakes and on first use; nothing needs continuous uptime. `npm run demo:seed -- --reset` removes every visitor order at once.
  - Abuse limits: at most `DEMO_MAX_VISITOR_ORDERS` (100) visitor orders retained (counted with the same predicate); at the cap, after cleanup, the order is refused with a 429 and a Hebrew message (the checkout already keeps the attempt on a 429); lower per-address order limits; the existing body, line, quantity and field-length limits; reviews and uploads off. The cap check is approximate under concurrency, acceptable at this size.
- **Tests and acceptance:** `test/smoke-demo-cleanup.js` on the test database: expired visitor orders are removed and recent ones stay; seeded orders (tagged), products, reviews, settings, pigment formulas and the marker are untouched; an order that has a non-demo phone is untouched; a forged tag cannot be created through the API (a non-UUID `request_id` is a 400); rerunning changes nothing; no marker, a wrong marker or `bootstrapping` deletes nothing; a bounded batch leaves the rest for the next run; the cap returns 429 and frees after cleanup; cleanup after a simulated long sleep (orders back-dated in the test) works on the next request; replay of a purged `request_id` creates a new order; reseeding after visitor orders exist neither duplicates nor deletes them.
- **Dependencies:** Phases 2 and 4. **Risks:** a wrong delete (marker, tag, phone predicate, tests); a slow first request after waking (bounded batch). **Rollback:** revert; set `DEMO_MODE` off.

- `node scripts/demo-candidates.js` — owner-run (read-only against the development database); the sheet is the approval record for products, images and pigment dosages.

- Source checks — agent-run: `rg -n "rejectUnauthorized[[:space:]]*:[[:space:]]*false|NODE_TLS_REJECT_UNAUTHORIZED" server scripts test` returns nothing; `rg -n "requireAdminRead" server/api --glob "*.routes.js"` shows only `router.get` lines (the unit suite enforces it).
- Live — owner-run: `curl -s https://<host>/api/health` returns `ok`; the rate-limit and forged-header curl tests from `docs/security.md`; `curl -sI https://<host>/` shows `Strict-Transport-Security`; a viewer write is 403 (browser network panel); the owner can edit a product; `POST /api/upload-multiple` is 403 for the owner; no email arrives; the banner is visible on every page.

## Risks
- Real personal data typed by a visitor: refused by the server (fixed identities), so never stored; the banner and read-only fields explain why.
- Role escalation: signed `role`, owner-only `requireAdmin` (default-deny), an explicit seven-route viewer allowlist limited to GET and HEAD, forged-token tests, no demo route outside demo mode, a 20-character owner password behind the login limiter. Residual: no revocation (rotate `SESSION_SECRET`).
- A viewer-readable endpoint exposing private data: only safe because a demo database holds only fictional values; the invariant check, the explicit column lists and the exposure test guard it. A real database must never run in demo mode: the marker, the pristine-database bootstrap and typed confirmations guard it.
- Demo and real databases confused: no flag skips the pristine check; the server never creates a marker; a normal server refuses a marked database.
- A half-finished bootstrap: `bootstrapping` is never served; resume needs the id.
- Cleanup deleting the wrong rows: tag, phone and marker predicates, a bounded batch, and regression tests. Residual: the tag is a convention on the `request_id` column (fallback: migration 013).
- Pigment dosages or catalogue data published by mistake: owner approval gates before any commit; the repository is public and history cannot be erased.
- Free-tier changes and cold starts (Render about one minute, Neon a short extra delay, the 5 s connection timeout in `server/config/db.js` may need a measured increase): accepted by the owner; facts re-verified before account creation.
- Rate limits are per process and per address; one instance only; a wrong proxy count breaks them (the live test decides).
- Migrations at startup with overlapping deploys: advisory lock; the direct host is required.
- The bootstrap scratch-database test needs the `CREATEDB` privilege; without it the suite is reported as not run.

## Rollback
Each phase is a separate reviewable change set and can be reverted on its own; with `DEMO_MODE` unset the application behaves as before. The hosted service and database are deleted from the provider dashboards by the owner. `demo-assets/` and `scripts/demo-data/` can be deleted without touching `uploads/`, `uploads-originals/`, `photos/` or `design-assets/`. No step reads or writes the development database except the read-only candidate listing, and no step writes to any database without the bootstrap and marker rules above.
