# 001 — Cloud deploy (closed and catalog modes)

Status: active
Owner: Idan
Last updated: 2026-10-22

## Goal
Run the admin on Render (free), with Postgres on Neon (free) and images on Cloudinary (free), so the owner's father can add products from a phone without the owner's computer being on. All three site modes are built, but the first deploy runs in `SITE_MODE=closed` (an under-construction page and the accessibility statement only). `SITE_MODE=catalog` (added 2026-10-22: the public can browse the partial catalogue, view-only, with a transparency banner, and nobody can order or pay online) is a later step with its own checklist in `docs/DEPLOY.md`, not part of this plan's rollout. Moving to `SITE_MODE=open` later restores the full store (pickup or delivery) by changing one setting, with nothing deleted. No fake content (demo reviews, invented statistics) may reach the public in any mode. There is no admin toggle for the mode: switching stays a deliberate change of `SITE_MODE` in Render. Instead (owner addition, 2026-10-22), an admin preview: in `closed` and `catalog`, a browser with a valid admin session sees the storefront as in `open` mode, under a slim fixed banner, while everyone else keeps the mode's behavior; order creation is still refused by the server in those modes, even in the preview. Local development keeps working exactly as today with no cloud account.

## Scope
In scope (the six parts of the task):
1. Storage adapter (`local` / `cloudinary`) behind `server/services/storage/`.
2. `SITE_MODE` (`open` / `catalog` / `closed`): `closed` = under-construction page, 503 on shop-only API, order creation refused, `robots.txt` and `noindex`; `catalog` = public view-only browsing with a banner, order creation refused on the server, and the cart, checkout, delivery choice and order lookup hidden in the client.
3. Production config: `DATABASE_URL`, small pool, SSL, tests that refuse a remote DB and use `TEST_DATABASE_URL`, CSP hosts, `render.yaml`, memory check of the upload path.
4. Order lookup needs phone + order number.
5. `npm run cloud:migrate-data` (dry run by default) and `npm run db:backup`.
6. `docs/DEPLOY.md` in Hebrew.

Out of scope: opening the store to ordering (`SITE_MODE=open` on the cloud is the owner's later decision), online payment, paid services, deleting local data, background removal on the server (stays a local tool), copying orders, and legal texts (privacy policy, terms), which need the owner or a professional. Added to scope on 2026-10-22: real-data hero statistics (step 8), a review list for the owner to confirm (step 13) and a migration that copies no review until then (step 11), and a new dry-run-first script that hides products without a real image (step 14), replacing `products:hide-unphotographed` for this rollout.

## Steps
1. Branch `feat/cloud-deploy` (created). Stage and hand over one commit per step below.
2. **Config.** `server/config/env.js`: optional `DATABASE_URL` (wins over `DB_*`; `DB_PASSWORD` stops being required when it is set), `DB_POOL_MAX` (default 10; 5 in `render.yaml`), SSL on for a non-local host, `STORAGE_DRIVER`, `CLOUDINARY_URL`, `SITE_MODE`. Unit tests in `test/unit-config.js` for each; `.env.example` gets names only.
3. **Test database guard.** `test/run-all.js` (and `scripts/a11y-audit.js`) refuse to start if `NODE_ENV=production` or the resolved URL's host is not local; they connect through `TEST_DATABASE_URL` (a separate local database, created with `createdb`, documented in README and `.doc/architecture.md`). Records the answer in AGENTS.md as the backlog item asks. Test for the guard.
4. **Storage module.** `server/services/storage/{index,local.driver,cloudinary.driver}.js` with `put`, `delete`, `url`, `getOriginal`/`putOriginal`/`deleteOriginal`. `image.service.processAndSave` returns the processed buffer and name; the upload middleware passes bytes to the driver instead of `fs.writeFile`. Processed images go to a public folder, originals as private assets. `image_url` stores what the driver returns (a relative `/uploads/...` for `local`, an `https://res.cloudinary.com/...` URL for `cloudinary`). Product validators accept both forms. Deleting a product deletes orphaned assets through the driver (an asset still referenced by another product is kept). One image at a time; `file.buffer` released after each. Tests: `unit-storage-local`, `unit-storage-cloudinary` (SDK mocked, no network).
5. **Reprocessing script.** `images:products --from-uploads` reads through the driver (download, process, upload) and works with both drivers; the local path is unchanged. `--target cloud` (with `--from-uploads` or `--revert` only) runs it on the cloud database and Cloudinary, with the credentials read from the environment file.
6. **Order lookup.** Server: lookup requires phone and order number, same rate limit, a generic "not found" for any mismatch (no hint which half was wrong). Client: "ההזמנות שלי" form with two fields, the success screen shows the order number prominently with the sentence that it is needed to check the order, the confirmation email carries it. Tests (server and client), docs.
7. **Site modes, server.** One `siteMode` helper reads `SITE_MODE` (`open` default, `catalog`, `closed`; an unknown value fails at startup). `closed`: middleware on the shop-only routes (products list/detail, reviews, order lookup, and `POST /api/orders`) returns 503 with a Hebrew message (admin session exempt, per Question 3). `catalog`: read routes (products, categories, approved reviews) work for everyone; `POST /api/orders`, the order lookup and, per Question 9, review submission are refused with a clear Hebrew message and a 4xx/503 status chosen from the `error-handling` skill's table; this is enforced on the server, so hiding the buttons is never the only protection. `GET /robots.txt` returns `Disallow: /` and `X-Robots-Tag: noindex, nofollow` is sent in `closed` and, per Question 11, in `catalog`. `/admin` and the admin API are untouched in every mode. **Admin preview:** the shop-only routes also let a valid admin session through in `catalog` (they are open to everyone there) and in `closed` (already exempt, Question 3), using the existing `markAdmin`; `POST /api/orders` is refused in `closed` and `catalog` for everyone, admin included, with the Hebrew refusal message (the checkout shows it as it shows any server message). `GET /api/site-mode` returns `{ mode }` to everyone and adds `adminPreview: true` only when `mode` is not `open` and the request carries a valid admin session; without a session, or with an expired or forged one, the answer is byte-for-byte the anonymous one, so it reveals nothing and, unlike `/api/auth/me`, never answers 401. Tests in all three modes, including order creation refused in `closed` and `catalog` (with and without an admin session) and still working in `open`, and `/api/site-mode` with no cookie, a forged cookie and a valid one.
8. **Site modes, client.** The server serves `/api/site-mode` (always 200) and the client reads it once. `closed`: every storefront route renders one "האתר בבנייה" page with address, hours and the store landline from `storeInfo.js` (plus WhatsApp only if `WHATSAPP_NUMBER` is set), its own neutral `<title>` (Question 19), `noindex` meta, keyboard- and screen-reader-accessible, styled with a new partial per `client/src/css/CONVENTIONS.md`; `/accessibility` is the one storefront route that stays reachable to everyone (it is served normally and is not wrapped), and the under-construction page links to it. **Hero statistics (all modes):** the home page reads the product count, the category count and the rating from the server (a small public endpoint, `GET /api/stats`, that returns only those numbers; it is a shop-only route and follows the same closed/catalog rules), applies Question 16, and hides the rating block when there are no approved reviews; `FeaturesBanner.js`, `WhyUs.js`, `About.js` and `HomePage.js` read the years from the `ESTABLISHED_YEAR` constant instead of the typed `30+`. Tests for each number and for the empty-rating case. `catalog`: first list every place the client touches the cart, checkout, delivery choice, order history and the paint calculator's add-to-cart (header cart control, product cards and pages, `CartStepView`, `DeliveryOptions`, `OrderHistory`, routes), then, behind the mode flag and without deleting any component: show a site-wide banner (Question 14) styled as a new partial; replace "add to cart" with a contact button (a call link to the store landline from `storeInfo.js`; WhatsApp only when `WHATSAPP_NUMBER` is set; icon reuse per `ui-and-styling.md`); hide the cart control; send `/cart` and the order-history route to the home page; keep the pickup address, hours and map visible; keep the accessibility statement linked in the footer. `/admin` routes are not wrapped. **Admin preview:** when `/api/site-mode` says `adminPreview`, the client renders the storefront exactly as in `open` (no under-construction page, no catalog banner, cart and checkout visible) under one slim fixed banner at the top, a landmark with the text "תצוגה מקדימה — האתר סגור לציבור" (`closed`) or "תצוגה מקדימה — האתר במצב קטלוג" (`catalog`) and a link to `/admin`; the banner is keyboard- and screen-reader-accessible, does not cover the header or the skip link (the page content is pushed down by its height, through a CSS custom property), and uses its own partial. A refused order shows the server's message. Client tests per mode (banner present, no add-to-cart, routes redirect), and for the preview in both modes (open behavior plus the correct banner text and link) and for a non-admin (mode behavior, no banner); `npm run a11y` covers the under-construction page, the accessibility statement in `closed`, the catalog banner and a product page in `catalog`, and the admin-preview banner in both modes (the audit logs in as admin for that pass).

## Risks
- A local run could connect to Neon by mistake: mitigated by `CLOUD_DATABASE_URL` naming (Question 4) and the test guard.
- Orphan deletion removes an image another product still uses: mitigated by checking references before `delete`, with a test.
- Cloudinary private assets or Render `/ws` behave differently than assumed: both are listed as unverified; the fallback is to keep originals in a non-public Cloudinary folder, and polling already works without `/ws`.
- Free-tier sleep (about a minute) confuses the father: documented in `docs/DEPLOY.md` section 7.
- Existing `/uploads/...` URLs in the local database must keep working locally and must not break the cloud copy: the migration rewrites URLs only in the target.
- Removing `/api/orders/by-phone/:phone` breaks any client still calling it: the client change ships in the same step and a test pins the new contract.
- The admin preview lets a visitor see the closed store: only a valid signed admin cookie unlocks it, `/api/site-mode` is identical for everyone else, and a test pins both.
- The preview makes the admin think orders work: the server refuses them in `closed` and `catalog` and the checkout shows the refusal, and the banner says the site is closed to the public.
- Demo or invented content reaches the public: no review is copied without the owner's id list, the hero numbers come from data, and the checklist makes the owner confirm both before `catalog`.
- The new hide script hides a product that does have an image (for example a file missing only in the local copy): the dry run lists every product and the reason before anything changes, and `--revert` restores the exact ids.
- The brand leaks through the Cloudinary cloud name or the Render URL: Question 18 and the name check in Validation.
- `catalog` is mistaken for a working store, and a visitor tries to order: the banner and the contact button say how to order, and the server refuses the order with a clear message, so no order is lost silently.
- The hidden cart or checkout code rots while unused: the `open`-mode client tests keep running in every `npm run test:client`.
- A partial catalogue shown as complete: the banner states it is partial; prices and stock may change.

## Rollback
Every step is a separate commit and reverts cleanly. The defaults (`STORAGE_DRIVER=local`, `SITE_MODE=open`, no `DATABASE_URL`) reproduce today's behavior, so a revert is not needed for local use. In the cloud, deleting the Render service stops everything; the Neon database and Cloudinary folder can be deleted from their dashboards; the local database and `uploads/` are never modified by this plan.
